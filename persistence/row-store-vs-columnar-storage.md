# Row-store vs Columnar 저장 + 백만 row 스캔

> "왜 인덱스를 걸어도 분석 쿼리가 본질적으로 느린가" = row-store 의 근본 페널티.
> breaking point ②(요청당 백만 row 스캔)의 원리. 관련: [OLTP vs OLAP](oltp-vs-olap-and-customer-facing-analytics.md).

---

## 1. 함정: 인덱스는 "찾기"를 돕지, "안 읽게" 해주진 않는다

예: **"내 에이전트 이번 시즌 총 거래액"** = `SUM(amount)` over 내 거래 100만 건.
- 인덱스 `(session_id, season)` 는 **어디 있는지** 완벽히 찾아줌.
- 하지만 `SUM` 은 그 **100만 row 를 실제로 다 만져야** 답이 나옴.
- **인덱스는 좁혀줄 뿐, 집계해주지 않음.** 답이 본질적으로 100만 row 에 달려 있으면 100만 row 를 읽는다.

---

## 2. row-store 근본 페널티 — 바이트 그림

### row 하나가 디스크에 눕는 모양
```
한 row (≈200 bytes), 컬럼들이 다닥다닥:
┌─────┬─────────┬────────┬───────────┬─────────┬───────┬──────────┬─────┐
│ id  │session  │ agent  │counterparty│ AMOUNT  │ price │occurred  │ ... │
│ 8B  │  8B     │  8B    │    8B     │  8B ★   │  8B   │   8B     │     │
└─────┴─────────┴────────┴───────────┴─────────┴───────┴──────────┴─────┘
                                        ★ = 우리가 원하는 8바이트 (다른 컬럼에 끼어 파묻힘)
```

### 8KB 페이지엔 이런 row 가 ~40개
```
8KB 페이지 1장:
[ row1 전체 200B ][ row2 전체 200B ] ... [ row40 전체 200B ]
      ★8B               ★8B                    ★8B
   └──── ★(amount)가 200바이트 간격으로 띄엄띄엄 ────┘
```

### 왜 ★만 못 읽나 — 이유 2개
1. **디스크/캐시는 바이트가 아니라 페이지(8KB) 단위로만 읽음.** "amount 8바이트만"이 물리적으로 불가능. 최소 단위가 페이지 한 장(= row 40개 통째).
2. **★들이 흩어져 있음** → ★ 100만 개 모으려면 흩어진 모든 페이지를 다 들춰야 함.

---

## 3. 페이지 산수

```
원하는 것:  ★ 100만 개 = 8B × 100만 = 8MB
실제 읽는 것: 100만 row ÷ 40(페이지당) = 25,000 페이지 × 8KB = 200MB

  200MB 읽어서 8MB 만 씀  →  효율 ≈ 4%
  나머지 192MB(딴 컬럼들)는 ★ 옆에 붙어 있다는 죄로 같이 끌려옴
```

비유: 엑셀을 **줄(row) 단위로 인쇄** → 5번 컬럼만 합산하려 해도 페이지마다 40줄 전체(25컬럼)가 찍혀 있어, 모든 페이지를 넘기며 나머지 24컬럼을 건너뛰어야 함. "5번 컬럼만 모은 묶음" 은 없음.

---

## 4. 지연 산수 — 왜 100ms 가 깨지나

- **최선(전부 캐시 hit)** 여도 CPU 가 **100만 row 순회**하며 컬럼 추출·합산 → 수~수십 ms.
- 캐시 miss → 디스크/OS I/O → 악화.
- **동시성**(유저마다 이 쿼리) → 합산 폭증 + churn 유발.
- → **요청 하나가 본질적으로 100만 row 를 건드리면 sub-100ms p95 물리적 불가.**

---

## 5. churn(①) 과 백만 row 스캔(②) 의 차이

| | ①churn | ②백만 row 스캔 |
|--|--------|----------------|
| 피해 대상 | **다른 쿼리**(OLTP) 캐시 오염 (부수 피해) | **이 쿼리 자체**가 느림 (본질적) |
| 캐시 데우면? | OLTP 회복 | **데워도 100만 row 읽기는 여전히 느림** |

→ 겹치면 최악 (백만 row 스캔이 churn 의 원인이기도).

---

## 6. 컬럼 지향(ClickHouse)이 왜 이기나

```
ClickHouse — 컬럼별로 따로 저장:
amount 블록:  [★][★][★][★][★]...  ← amount 만 빽빽이 연속 (+압축 LZ4/ZSTD)
              → 이 블록(8MB)만 쭉 읽음. 다른 컬럼 블록은 손도 안 댐
```

| | Row store (PG) | Column store (CH) |
|--|----------------|-------------------|
| 1컬럼 집계 | row 전체(200MB) 읽음 | 그 컬럼(8MB)만 |
| 실행 | row 하나씩 | 벡터화(SIMD) |
| 인덱스 | row 마다 B-tree | granule(8192행)당 마크 1 = sparse |
| 압축 | 낮음 | 높음(동종 컬럼) |

→ 분석 집계 **10~100x.** 그래서 OLAP 를 **PG 옆에** 둠 = 역할 분리(§ [OLTP vs OLAP](oltp-vs-olap-and-customer-facing-analytics.md)).
